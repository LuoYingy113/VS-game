# Team Matcher 技术架构

本文描述仓库当前采用的技术、运行组成、模块层次和调用关系，可作为绘制系统技术架构图的依据。架构图建议按“客户端、HTTP 接入、后端应用、数据持久化、外部服务”分层，并用实线表示同步请求、虚线表示邮件或设备集成。

## 1. 总体架构

```mermaid
flowchart LR
  subgraph Client[客户端：Expo 跨平台应用]
    UI[React Native 角色界面]
    Shell[应用入口与共享状态<br/>src/app/index.tsx]
    APIClient[API 客户端<br/>src/api.ts]
    Local[本地存储<br/>AsyncStorage]
    Device[设备能力<br/>日历、电话、邮件、外部链接]
    UI --> Shell
    Shell --> APIClient
    Shell <--> Local
    UI -.调用设备能力.-> Device
  end

  subgraph Server[服务端：FastAPI 单体应用]
    Routes[REST API 路由<br/>main.py]
    Contracts[Pydantic 请求/响应模型]
    Logic[路由内业务规则与流程处理]
    ORM[SQLAlchemy ORM<br/>models.py]
    Lifecycle[生命周期任务<br/>启动迁移/种子数据/过期比赛清理]
    Routes --> Contracts
    Routes --> Logic
    Logic --> ORM
    Lifecycle --> ORM
  end

  DB[(PostgreSQL)]
  SMTP[SMTP 邮件服务<br/>默认 Gmail SMTP]
  AppBuild[Expo / EAS 构建与分发]
  Maps[Google Maps 网页链接]

  APIClient -->|HTTP(S) JSON /api| Routes
  ORM -->|SQLAlchemy PostgreSQL 驱动| DB
  Logic -.验证、验证码、监护关系邮件.-> SMTP
  Device -.地图跳转.-> Maps
  Client -.原生构建/提交.-> AppBuild
```

> 注：图中的“业务规则与流程处理”是对当前 FastAPI 路由内部逻辑的归纳，并非独立部署的业务服务层。

## 2. 技术栈与第三方集成

| 层次 | 技术/服务 | 在系统中的用途 |
| --- | --- | --- |
| 前端语言 | TypeScript | 客户端业务代码和领域类型定义 |
| 跨平台运行时 | Expo SDK 57、React Native 0.86、React 19 | iOS、Android 和 Web 客户端运行基础 |
| 客户端导航 | Expo Router、React Navigation | 应用入口和导航依赖；根布局配置为 Stack，主要业务界面由角色屏幕承载 |
| 前端网络 | Fetch API | 调用后端 `/api` REST 接口；统一处理 JSON、超时和网络错误重试 |
| 本地存储 | `@react-native-async-storage/async-storage` | 保存登录用户标识、比赛提醒去重数据及部分历史信息缓存 |
| 后端框架 | Python、FastAPI | 提供 HTTP API、依赖注入、CORS 和生命周期入口 |
| API 契约 | Pydantic | 请求参数校验及响应模型定义 |
| ORM | SQLAlchemy | 数据模型映射、数据库会话和查询操作 |
| 关系数据库 | PostgreSQL | 持久化用户、球队、比赛、名单、通知和设置等业务数据 |
| 邮件 | SMTP；默认 SMTP 主机为 Gmail SMTP | 邮箱验证、验证码、密码流程和监护关系确认邮件；通过服务端环境变量配置 |
| 系统日历 | Expo Calendar | 将比赛事件写入 iOS/Android 设备的可写日历 |
| 外部应用 | Google Maps URL、系统 `tel:` / `mailto:` 链接 | 从客户端跳转地图、拨号或邮件应用，不是本项目自建服务 |
| 构建分发 | Expo Application Services（EAS）配置 | 定义 development、preview、production 构建/分发配置 |
|外部服务 / API|地理编码与距离计算 API（如 Google Maps Geocoding 或同类服务）|后端根据比赛及球队地点调用 API 获取经纬度，用于支撑智能搜寻的距离与评分计算

版本以仓库 `package.json`、`app.json` 和 `eas.json` 为准。后端仓库未提供 `requirements.txt` 或 Python 锁文件，因此 Python 依赖的精确版本及可复现安装清单尚未由仓库固定。

## 3. 前端技术层次

```text
表现层
  ├── src/app/index.tsx：应用状态容器、登录恢复、角色选择、全局通知和提醒
  ├── src/screens/LoginScreen.tsx：登录、注册、验证码和密码流程
  ├── src/screens/CoachScreen.tsx：教练工作台
  ├── src/screens/PlayerScreen.tsx：球员工作台
  ├── src/screens/GuardianScreen.tsx：监护人工作台
  ├── src/screens/AdminScreen.tsx：管理员设置
  └── src/components/：共享表单、导航、弹窗、提示等 UI 组件

客户端应用/状态层
  ├── src/app/index.tsx：加载共享业务数据并按角色分发
  ├── React state：当前用户、用户、比赛、球队、申请、名单、设置和通知等
  └── src/types.ts：客户端领域对象与组件间数据契约

客户端服务层
  ├── src/api.ts：HTTP 请求、API 地址、超时/重试、DTO 映射、初始数据聚合
  ├── src/storage.ts：通知 API 辅助、本地会话和提醒去重/缓存
  ├── src/i18n.tsx：语言上下文和翻译表
  └── src/calendar.ts：设备日历读写封装

平台适配层
  ├── Expo / React Native：iOS、Android、Web 运行支持
  ├── AsyncStorage：本地键值持久化
  └── Expo Calendar、Linking：访问设备或外部应用能力
```

角色屏幕通过 `src/app/index.tsx` 接收共享状态和更新方法；各屏幕可调用 `src/api.ts`，也存在页面直接使用 `apiFetch()` 的情况。API 层把后端 `snake_case` 字段映射为前端 `camelCase` 类型，减少 UI 对传输格式的直接依赖。

## 4. 后端技术层次

```text
HTTP 接入层
  └── FastAPI app：/api 路由、CORS、中间件配置和 lifespan

接口契约层
  └── main.py 中的 Pydantic 模型：请求字段校验及响应结构

业务处理层（当前与路由同文件）
  ├── 身份、注册、邮箱验证和账号资料
  ├── 俱乐部、球队分组、邀请码和成员关系
  ├── 比赛、对战申请、比赛发生确认和教练历史
  ├── 球员参赛名单、监护审批和通知
  └── 系统设置、邮件发送及过期比赛清理

数据访问层
  ├── database.py：PostgreSQL SQLAlchemy engine、SessionLocal、Base 和 DB session 依赖
  └── models.py：SQLAlchemy ORM 表模型

持久化层
  └── PostgreSQL 数据库
```

当前 `main.py` 同时包含应用配置、路由、Pydantic 模型、部分业务规则、邮件工具、迁移/种子逻辑和后台任务。`models.py` 定义 ORM 模型，`database.py` 创建数据库连接及会话依赖。项目没有独立的微服务、消息队列或单独部署的业务服务层。

## 5. 主要模块及关系

### 5.1 客户端模块

- **应用入口与角色界面**：入口加载所需业务集合，再将共享状态传递给教练、球员、监护人或管理员屏幕。
- **API 与 DTO 映射**：角色界面通过 `apiFetch` 访问 FastAPI；`loadAllData()` 并发获取主要业务数据，映射函数转换 User、Game、TeamGroup、Club、Roster 和 MatchApplication 等对象。
- **本地持久化**：登录用户 ID 和比赛提醒去重记录保存在 AsyncStorage；通知主体保存在后端，客户端轮询获取。
- **设备集成**：日历写入经 Expo Calendar 完成；地图、电话和邮件通过操作系统链接交由外部应用处理。
- **比赛发现与智能排序交互**：在比赛发现组件中新增智能搜索开关按钮；将计算得出的综合评分字段适配到前端渲染逻辑中，实现按分排序。

### 5.2 服务端模块

- **认证与用户**：依赖 User、InviteCode、CoachInviteCode 和监护关系模型；与 SMTP 邮件工具协作完成验证和确认流程。
- **组织管理**：Club、TeamGroup、User 表示俱乐部、球队分组和成员关系；邀请码支持加入球队。
- **比赛撮合**：Game 描述比赛；MatchApplication 描述教练/球队的对战申请。接受申请后，服务端更新比赛对手状态，并创建相关 Roster 邀请及 Notification。
- **参赛审批**：Roster 连接比赛与球员，记录邀请、监护审批、教练审批、退出等状态；监护关系来自 User 关联和 GuardianPlayerLinkRequest。
- **比赛记录与设置**：GameOccurrenceConfirmation 记录双方教练的发生确认；双方确认后累计教练比赛次数。CoachGameHistory、CoachPlayerNote 保存教练扩展信息；Settings 保存全局年龄阈值。
- **通知与邮件**：业务路由在需要时写入 Notification 或调用 SMTP 邮件工具；客户端通过定时轮询同步站内通知。
- **生命周期任务**：应用启动时运行迁移和演示数据初始化；后台任务扫描并清理过期比赛及关联记录。
- **智能检索与计分逻辑**：在 FastAPI 路由/业务层中集成地理位置解析与距离算法，串联“经纬度获取 $\rightarrow$ 距离计算 $\rightarrow$ 年龄差计算 $\rightarrow$ 综合加权计分 $\rightarrow$ 排序返回”的处理链路。

## 6. 端到端数据流

### 6.1 一般业务请求

```text
用户在角色屏幕提交操作
  → 页面构造 JSON 请求
  → src/api.ts 发送 HTTP(S) 请求到配置的 API Base URL
  → FastAPI 路由校验 Pydantic 请求模型
  → 路由业务逻辑读写 SQLAlchemy 模型
  → PostgreSQL 提交事务
  → FastAPI 返回 JSON
  → api.ts 映射传输字段并更新共享状态/UI
```

API Base URL 可由 `EXPO_PUBLIC_API_BASE_URL` 指定；源码含有默认地址。服务端使用 `CORS_ALLOW_ORIGINS` 配置允许来源。

### 6.2 邮件流程

```text
注册/验证码/监护绑定业务
  → FastAPI 业务路由生成验证内容或链接
  → SMTP_SSL 连接配置的邮件服务器
  → 收件人的邮箱客户端打开验证码或确认链接
  → 链接回到 FastAPI 对应 API
```

SMTP 主机、端口、发件人、应用密码和应用公共 URL 通过服务端环境变量配置。邮箱验证码当前有服务端存储逻辑，并带进程内存回退；不是独立消息队列。

### 6.3 通知与本地提醒

```text
业务事件 → Notification 数据库记录 → 客户端定时请求通知 API → 更新收件箱和未读数
比赛时间检查 → AsyncStorage 去重记录 → 通过通知 API 写入站内提醒
```

当前通知采用客户端轮询，不是 APNs/FCM 推送架构。

## 7. 运行与部署边界

- **客户端运行**：Expo 开发服务可运行原生 iOS/Android 客户端，也支持 Web；`app.json` 将 Web 输出配置为静态模式。
- **客户端构建**：`eas.json` 定义开发、预览和生产构建配置；该配置表明 EAS 构建集成，不代表仓库包含完整的自动部署流水线。
- **服务端运行**：FastAPI 作为单体应用运行，可由 ASGI 服务器（例如 Uvicorn）启动；具体生产进程管理、反向代理、TLS 终止和容器编排不由仓库配置完整描述。
- **数据库连接**：当前 PostgreSQL SQLAlchemy DSN 在 `database.py` 中创建。该文件目前直接定义连接串；部署架构图不应展示任何凭据，生产环境应使用受保护的环境变量或密钥管理设施。
- **配置边界**：前端 API URL、CORS、SMTP 和邮件链接均依赖配置。前后端通过 HTTP(S) JSON API 耦合，不共享数据库连接。
- **依赖管理边界**：前端依赖由 `package.json` 管理；仓库未提供后端依赖版本锁定文件。

## 8. 绘图建议

建议在技术架构图中用五个区域表达系统：

1. **用户端/设备**：iOS、Android、Web；角色 UI、应用状态、API 客户端、本地存储和系统日历。
2. **网络接口**：HTTP(S) JSON、`/api`、CORS、可配置 API Base URL。
3. **后端应用**：FastAPI 单体；接口模型、路由内业务逻辑、生命周期任务、邮件工具。
4. **数据层**：SQLAlchemy、PostgreSQL、业务表和关系。
5. **外部服务**：SMTP 邮件、Expo/EAS 构建、系统日历、Google Maps/系统拨号与邮件链接。

模块连线重点：客户端角色界面 → API 客户端 → FastAPI 路由/业务逻辑 → SQLAlchemy → PostgreSQL；业务逻辑 → SMTP；客户端 → AsyncStorage；客户端 → 系统日历/地图等设备或外部应用。用注释注明：通知为轮询、后端为单体、没有消息队列，部署拓扑与 CI/CD 未由当前仓库完整定义。
