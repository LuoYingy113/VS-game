# Team Matcher 功能架构说明

## 1. 项目定位

Team Matcher 是面向球队与赛事协作的跨平台应用。系统围绕“俱乐部/球队组织 — 比赛撮合 — 队员参赛 — 监护审批”组织功能，为教练、球员、监护人和管理员提供不同工作入口。

## 2. 总体功能架构

```text
Team Matcher
├── 客户端：Expo + React Native
│   ├── 应用入口与共享状态（src/app/index.tsx）
│   ├── 登录、注册与身份入口（LoginScreen）
│   ├── 角色工作台
│   │   ├── 教练工作台（CoachScreen）
│   │   ├── 球员工作台（PlayerScreen）
│   │   ├── 监护人工作台（GuardianScreen）
│   │   └── 管理员工作台（AdminScreen）
│   ├── API 访问、DTO 映射（src/api.ts）
│   ├── 本地持久化与通知辅助（src/storage.ts）
│   └── 共享组件、类型、日历与多语言
├── 服务端：FastAPI（main.py）
│   ├── 账号、角色、注册与验证
│   ├── 俱乐部、球队分组与邀请
│   ├── 比赛发布、发现、申请与确认
│   ├── 名单、参赛状态与监护审批
│   ├── 通知、系统设置与比赛记录
│   ├── 邮件服务、后台清理与启动初始化
│   └── SQLAlchemy 数据访问（models.py / database.py）
└── 持久化数据
    ├── 用户与监护关系
    ├── 俱乐部、球队分组与球员
    ├── 比赛、对战申请与参赛名单
    ├── 通知、邀请码与系统设置
    └── 教练比赛历史、比赛发生确认与球员备注
```

客户端典型调用链：

```text
用户操作
  → 角色工作台
  → src/api.ts（请求封装、超时/网络重试、snake_case/camelCase 映射）
  → FastAPI 路由与业务规则
  → SQLAlchemy 模型 / 数据库
  → 响应映射回客户端共享状态并更新界面
```

通知和邮件是业务流程的横向支撑能力：服务端可在关键业务节点创建通知或发送验证邮件；客户端轮询当前用户通知并展示收件箱、未读数和比赛提醒。

## 3. 客户端功能模块

### 3.1 应用入口与公共能力

`src/app/index.tsx` 是客户端组合入口，负责初始数据加载、登录用户恢复、角色路由、共享状态维护、刷新与登出，以及通知轮询和比赛时间提醒。用户具有多个角色时，可在其可用角色间切换。

公共支撑模块包括：

- `src/api.ts`：统一 HTTP 请求、基础 URL、重试策略和后端数据映射；`loadAllData()` 汇总加载用户、比赛、球队分组、申请、名单、设置和俱乐部数据。
- `src/storage.ts`：保存登录用户标识、比赛提醒去重信息，并封装通知读写辅助。
- `src/i18n.tsx`：提供英文、中文和希腊语的语言表与语言上下文。
- `src/types.ts`：定义用户、比赛、俱乐部、球队分组、名单、对战申请、通知等客户端领域类型。
- `src/calendar.ts` 与共享组件：提供系统日历添加、通用弹窗、导航和反馈等能力。

### 3.2 登录、注册与账号

- 邮箱/密码登录及邮箱验证码登录。
- 教练和球员注册；未成年人注册可同时提交监护人信息。
- 邮箱验证、验证码发送、密码重置和密码修改。
- 个人资料维护；球员和监护人可维护各自资料，教练可维护运动项目、默认地点、俱乐部等信息。
- 通过登录状态恢复和退出登录管理客户端会话。

### 3.3 教练工作台

- **比赛发现**：按运动项目、年龄组、性别等筛选比赛；可通过比赛邀请码查看私有比赛，并选择所属球队提交对战申请。
- **我的比赛**：创建、查看、编辑或取消比赛；处理其他教练的对战申请。接受申请后锁定对手，并进入球队参赛名单管理。
- **已确认比赛**：查看已锁定比赛、对手和比赛信息，管理参赛名单与人员状态。
- **俱乐部与球队管理**：创建和管理俱乐部、球队分组；设置年龄组、性别、运动项目和所属俱乐部；管理正式球员与线下球员，移动或移除球员，并管理球队邀请码。
- **参赛名单管理**：邀请球员、查看邀请/待审批/已批准/不参加/退出等状态，并处理教练侧参赛确认。
- **个人及比赛记录**：维护教练资料；记录比赛结果与备注、球员昵称；查看比赛发生确认和教练比赛次数等信息。

### 3.4 球员工作台

- 查看收到的比赛邀请并接受或拒绝/不参加。
- 查看个人赛程；对已批准的参赛可退出并填写原因，或更新参赛意向。
- 通过球队邀请码加入球队，并查看已加入球队。
- 维护个人资料；将已确认比赛添加到设备日历。

### 3.5 监护人工作台

- 通过邮件确认流程关联球员账号，并选择当前管理的球员。
- 查看关联球员待监护审批的参赛请求并批准；批准后请求转入教练确认阶段。
- 查看关联球员赛程，并报名或取消比赛志愿者。
- 维护监护人资料。

### 3.6 管理员工作台

- 配置全局未成年人年龄阈值。
- 生成教练注册邀请码。

当前管理员界面集中于上述系统设置和教练邀请码，不应将其描述为已具备完整的用户运营、审核或平台数据管理后台。

## 4. 服务端业务模块

服务端主要集中在 `main.py`，按路由和模型逻辑分区实现；目前是单体 FastAPI 应用，而非拆分部署的微服务。

| 业务模块 | 主要职责 |
| --- | --- |
| 账号与认证 | 登录、注册、邮箱验证、验证码登录、密码重置、资料维护、账号删除及角色信息 |
| 邀请码 | 球员加入球队的邀请码、比赛访问邀请码、教练注册邀请码及兼容的旧邀请码 |
| 用户与监护关系 | 用户查询和资料更新；监护人与球员的关联请求及邮件确认 |
| 俱乐部与球队分组 | 俱乐部和球队分组的创建、修改、删除；成员移动、加入、移除及线下球员管理 |
| 比赛 | 比赛查询、私有比赛邀请码查询、创建/修改/删除、志愿者维护及历史查询 |
| 对战申请 | 创建申请、去重、接受/拒绝；接受时锁定对手，并为相关球员创建参赛名单和通知 |
| 参赛名单 | 批量创建邀请、更新球员参赛状态，并维护监护审批标记和退出原因 |
| 比赛发生确认 | 两位对阵教练分别提交确认；双方确认后更新比赛发生状态并累计教练比赛次数 |
| 教练扩展记录 | 教练比赛结果/备注、教练对球员昵称备注 |
| 全局设置 | 保存和读取未成年人年龄阈值 |
| 通知 | 创建通知、按用户查询通知、批量标记已读 |
| 生命周期任务 | 启动时执行迁移和演示数据初始化；后台清理过期比赛及其关联数据，并通知相关教练 |
| 邮件支撑 | 邮箱验证、验证码、密码流程、监护关系确认等邮件发送 |

## 5. 核心业务流程

### 5.1 球队组建与加入

```text
教练创建俱乐部（可选）
  → 创建球队分组并配置运动项目/年龄组/性别
  → 添加正式球员或线下球员、生成球队邀请码
  → 球员通过邀请码加入球队
```

球队分组是教练组织球员、创建比赛和选择对战申请队伍的主要业务单元。

### 5.2 比赛撮合与参赛名单

```text
教练创建公开或私有比赛
  → 其他教练发现比赛或输入比赛邀请码
  → 选择球队提交对战申请
  → 主办教练接受申请
  → 比赛锁定对手，服务端创建球员参赛邀请
  → 球员响应邀请
  → 视年龄与监护关系进入相应审批状态
  → 教练确认参赛名单
```

申请状态与名单状态分属不同业务对象：对战申请描述球队间的比赛匹配；参赛名单描述单个球员是否参加该场比赛。

### 5.3 未成年人参赛审批

```text
球员接受邀请
  → 未成年人且已关联监护人：pending_guardian
  → 监护人批准：pending_coach，并记录 guardian_approved
  → 教练确认：approved
```

成年人或不需要监护审批的球员按服务端规则进入教练确认流程。球员也可以更新参赛意向或退出；退出记录原因，并受服务端状态规则约束。

### 5.4 比赛完成确认

```text
对阵双方教练分别提交比赛发生确认
  → 双方均确认后，比赛标记为已计入
  → 更新双方教练的比赛次数
```

## 6. 核心数据对象

- **User**：账号、角色、联系方式、球员资料及监护人关联。
- **Club**：教练拥有的俱乐部及默认地点。
- **TeamGroup**：教练创建的球队分组，关联俱乐部、成员、年龄组、性别和邀请码；可包含线下球员。
- **Game**：比赛发布信息、主队/对手、状态、私有访问码及志愿者等。
- **MatchApplication**：教练为球队提交的比赛申请及其处理状态。
- **Roster**：球员与比赛的关联、参赛状态、监护审批结果和退出原因。
- **Notification**：面向用户的站内通知及已读状态。
- **Settings**：平台级未成年人年龄阈值。
- **InviteCode / CoachInviteCode**：球员入队或教练注册相关邀请码。
- **GuardianPlayerLinkRequest**：监护人关联球员的确认请求。
- **CoachGameHistory / GameOccurrenceConfirmation**：教练比赛备注/结果及双方比赛发生确认。
- **CoachPlayerNote**：教练私有的球员显示昵称备注。

主要关系可概括为：教练拥有多个俱乐部和球队分组；球队分组包含球员并参与比赛；比赛关联主办教练、主队、对手、对战申请和球员名单；用户之间可通过监护关系关联。

## 7. 横向支撑与架构特点

- **通知**：比赛申请、申请处理、球员邀请、审批和比赛提醒等场景使用站内通知；客户端定期读取通知并展示未读状态。
- **邮件**：支撑邮箱验证、验证码、密码流程和监护关系确认；邮件发送依赖服务端 SMTP 配置。
- **时间与数据清理**：客户端定期检查即将开始的相关比赛并发送去重提醒；服务端后台任务清理超过期限的比赛及关联数据。
- **国际化与设备集成**：客户端提供多语言文本，并支持将已确认比赛写入系统日历。
- **当前实现形态**：前端采用单一应用入口集中持有共享状态，再将状态传给按角色划分的大型屏幕组件；API 封装同时承担网络请求和 DTO 映射。后端路由、模型契约、业务规则、生命周期和邮件逻辑主要集中在 `main.py`，数据库模型位于 `models.py`。该说明描述现有实现边界，不代表已具备独立服务化或细粒度权限中间件架构。
